## Rules

- **Core is the only source of numbers.** Review findings from `DesignReview.Run(kind, build,
  catalog)` (`ReviewReport.Issues`, `Blockers`, `Majors`, `Minors`, `PassAllowed`); rework fee from
  `DesignReview.ReworkFeeM`, rework from `DesignReview.Rework`; FRR poll logic from
  `FrrPoll.Record(go, noGo)` (`Go`, `DiscussAndRepoll`, `ReworkOffered`,
  `FrrPoll.DiscussionSeconds` = 15 s); test offers from `TestCampaign.Available` / `Offer`, results
  from `TestCampaign.Run(..., minigameTier)` (`TestOutcome.FlawRevealed`, `RevealChance`, `Roll`,
  cost and days in the ledger), flaw handling from `TestCampaign.FixFlaw` and the `test_failure`
  card through `AnomalyDeck.DrawSpecific` / `Respond`; the uncertainty band before and after a test
  from `Dashboard.Compute`; contract offers from `ContractsBoard.Offer` (campaign) or the host's mode
  rules (Quick Mission; `MissionSetupRules.FixedContractId` locks one). Never recompute a rule in
  Unity; a rehearsal fixture is data, not logic.
- **The room server is the authority for votes and polls.** The host sends `vote.open` (with the
  per-option numbers it computed) and `vote.commit`, and renders `vote.opened`, `vote.stage`,
  `vote.tally`, `vote.result`, `vote.cancelled` exactly as `protocol/messages.md` defines them. The
  GO/NO-GO ritual is `poll.open` → `poll.call` → `poll.answered` → `poll.result`; the host decides
  what follows. Timers use `endsAtMs` corrected by the clock offset from `clock.ping/pong`, never a
  local guess. Hidden tallies stay hidden.
- **Phase announcements:** `phase.set` with `phase` BRIEFING, CONTRACT_VOTE, BUILD (`sub` TEST or
  REVIEW with `review` PDR / CDR while your screens are up), FRR (`review` FRR), per protocol
  section 6. Transitions go through the app's `SceneFlow` / `GamePhaseMachine`; do not invent new
  phases.
- **Look:** release quality, no default UI, no debug text, no placeholder art. 32 px body / 24 px
  labels / 64 px titles at 1920×1080; every number with its unit; severity and GO / NO-GO as colour
  **plus** shape, label and border (Blocker = Fails octagon, Major = Marginal triangle, Minor =
  outlined circle with "Minor"; GO = Meets, NO-GO = Fails, no answer = muted dashed); the NASA
  lifecycle tag on each screen (2.3: "PRE-PHASE A · CONCEPT STUDIES", "PHASE B · PDR", "PHASE C ·
  CDR", "PHASE D · FRR"). Panels mirror for right-to-left languages. Keyboard and gamepad focus with
  a visible Signal outline. Text from `data/strings/en*.json`; existing keys first (`contract.*`,
  `test.*`, `validation_rule.*`, `anomaly.*`, `role.*`), new ones only in your fragment.
- **Real tragedies** (Apollo 1, Challenger, Columbia) are never test or review outcomes or jokes
  (12.1). Test failures are engineering findings, shown calmly.
- **WebGL first:** UI Toolkit; built-in Particle System; Shader Graph or URP HLSL that compiles for
  WebGL 2; no VFX Graph, no compute shaders. Video in WebGL must play from a URL (StreamingAssets),
  not from an imported `VideoClip`. Unity units: metres, +Y up.
- **Rehearsal:** every screen has a rehearsal driver (editor and development builds only, labelled
  "REHEARSAL" on screen) that feeds synthetic, seeded `vote.*` / `poll.*` envelopes for 1, 4 and 10
  players through the same handlers, so each screen can be shown without phones.

## Interface this task provides

In `Screens/Preflight/Runtime/` (asmdef `MissionForge.Preflight`, references `MissionForge.Core`,
`MissionForge.App`, `MissionForge.Net`, `MissionForge.Data`; document it in
`Screens/Preflight/README.md`):

- `PreflightSchedule.After(BuildState, GameCatalog, string committedSlot) → Interlude` where
  `Interlude` is `None`, `TestOffer(TestOffer)`, `Review(ReviewKind)`. Rules (decisions, tag them
  `game_value` in the README): offer at most one test per committed vote, the first applicable offer
  for the just-committed part in `data/tests.json` order that has not run; PDR once the next vote's
  6.2 step is 16 (avionics) or later, or no votes remain; CDR when no votes remain; whole-vehicle
  tests (wet dress rehearsal) are offered once, just before CDR. FRR is a phase, not an interlude.
- `TestStandFlow` and `DesignReviewFlow`: `Task<BuildState> RunAsync(BuildState, …)` style entry
  points that show the screen, run the quick votes and return the new build (and, for a Rework, the
  reopened category so the Build Bay's re-vote can call `DesignReview.CompleteRework`).
- `PreflightEvents`: `ContractChosen(contractId)`, `TestCompleted(TestOutcome)`,
  `ReviewClosed(kind, passed)`, `FrrConcluded(PollOutcome, pollResult)`.
- **Build Bay hook:** if T015's `BuildBayDirector` is on `main`, it should call
  `PreflightSchedule.After` after each `vote.commit` and await the flow it names. Do not edit
  T015's folder: if the call is missing, run your flows from your rehearsal driver, and write the
  exact call T015's owner must add under **Interface changes**.
- **MG-07 hook:** the FRR does not start minigames. On an all-GO result raise
  `PreflightEvents.FrrConcluded(Go, …)` with the console call order; T026's `MinigameDirector` (if on
  `main`) fires MG-07 at countdown F1 from that event. Test minigames (MG-03, MG-04, MG-06, from
  `TestDef.MinigameId`) are requested through the same director when present and their tier is
  passed to `TestCampaign.Run`; without T026, tier 0 and say so.
