# T060: static protocol check, Unity host vs room server and phone client

Static, read-only comparison of every message the Unity host (`unity/MissionForge/Assets/MissionForge/`, T027 included: PR #231) sends or
handles against the room server (`server/src`), the phone client (`client/src`) and the protocol (`protocol/messages.md`,
`protocol/schema/`). Nothing was built or run, and no Unity, server or client file was changed. The task was started by
`mohammed-alainieh` (stopped by a usage limit, nothing pushed) and finished by `momansy-claude` with three read-only reviewers, one per
phase group: **A** connection, lobby, settings, phase, pause, briefing; **B** contract vote, Build Bay, reviews, test stand, abilities;
**C** countdown, flight, minigames, debrief. Their full tables follow. Each row says match or mismatch, and each mismatch is marked
**blocks-session** (a real session would stall, or messages are rejected) or **cosmetic**.

## Summary: what to fix on the Unity side first (for yousuf-amek)

| # | Mismatch | Severity | Effect in a real session | Where |
|---|---|---|---|---|

| 4 | REWORK_CATEGORY `vote.open` right after the REVIEW result: the host finishes on `vote.result`, the server keeps the round active until `vote.stage` CLOSED | blocks-session for the rework feature, no stall | ROUND_ACTIVE on all 3 instant retries, then the host applies `slots[0]` with no vote (`DesignReviewScreen.cs:105`, `FrrScreen.cs:168`, `PreflightScreen.cs:52-67`) | part B |
| 5 | Host never handles `ability.requested` or sends `ability.resolve` | blocks-session for abilities only | Every non-FLIGHT ability ends in `ABILITY_REJECTED` after the server's 5 s timeout; FLIGHT Decision Time works because the server resolves it | parts B, C |

Everything else is cosmetic. The most visible cosmetic ones: `phase.set` is sent once per top-level phase, so the phone flight header stays on
"F2" for the whole flight; `mg.summary.boosts` is always empty; cooperative minigames (COOP_SPLIT, RELAY, TEAM_SYNC) get no assignments,
so phones fall back to a simulated crew; `contractId` and `step` are null in the generic `phase.set`, so the spectator screen can lose the
contract name; the host never sends `room.close`; reconnect back-off is 15 s on the host and 5 s on the phone.

**Server versus spec (not host-caused):** the server is more lenient than `protocol/messages.md` (it does not enforce INVALID_TRANSITION,
STALE_ID, DUPLICATE_ID and ROUND_ACTIVE for `mg.*`, UNKNOWN_PLAYER, WRONG_PHASE, NOT_ROLE_HOLDER). The host is not affected by this.

**Matching, so no action:** `hello`/`hello.ok`, `clock.ping`/`pong`, `error`, `bye`, `room.create`/`created`/`resume`/`resumed`/`state`,
`settings.set`/`state` (all fields and enums), `phase.set` required fields and top-level graph, `game.paused`/`resumed`, the reconnect
sequence, contract vote and Build Bay `vote.*` messages, `ping.event`, all `poll.*` for FRR, TEST/REVIEW/ANOMALY option ids,
`flight.hud` (all 13 fields), `mg.start` (all 31 catalog parameter sets), `mg.summary`, `mg.cancel`.

**Limits of this check:** static reading only, so timing, WebGL-specific behaviour and anything a running Unity player does is not covered
(the real-host runs of T055 and T061 cover that; their defects were not cross-checked line by line against this report). Items marked
"unverified" in the tables could not be confirmed from the code. Client-side fixes were not attempted because the client freeze (11:30 UTC)
had passed; none of the blocking items above is a client or server bug, they are all on the host.
